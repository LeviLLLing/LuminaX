# LuminaX 产品级重构设计规格

**日期：** 2026-08-11  
**状态：** 已批准，待实施计划  
**目标版本：** 可扩展本地 POC  
**实施方法：** Superpowers 兼容性垂直切片

## 1. 背景

LuminaX 已具备登录认证、权限管理、自定义指标注册、固定 SQL 指标计算、经营报表、三 Agent 编排、MySQL 数据源和 SQL Server 数据源接口。项目经过多轮功能增加与模块拆分后，业务能力基本成形，但产品结构、代码边界、测试组织和项目文档出现明显漂移：

- `AGENTS.md` 仍描述本地 JSON 和 JavaScript 计算，与当前 DeepSeek、多 Agent、MySQL、权限体系不一致。
- `README.md` 保留较多初始模板内容，不能作为可靠运行手册。
- 前台仍偏向单一对话演示，缺少通用工作台、角色模板和权限投影之间的清晰关系。
- 管理后台以大型单页组件承载指标与权限功能，后续增加报表、数据源和 Agent 配置时难以扩展。
- 固定 SQL、MySQL 执行器、权限面板和指标面板存在超大文件。
- 所有自动化测试集中在一个测试文件中，所有权和失败定位不清晰。

本次重构以“完整兼容”为硬约束，提升产品成熟度、模块清晰度、测试可信度和后续扩展能力，不改变现有业务口径和外部接口。

## 2. 产品定位与用户

### 2.1 产品定位

LuminaX 是通用经营智能工作台。它通过统一的指标计算、AI 问答、经营归因和报表能力，帮助有权访问经营数据的用户发现问题、解释原因并形成行动建议。

工作台不绑定某个固定岗位。岗位差异由角色模板表达，真实数据与操作边界由权限系统决定。

### 2.2 演示与使用关系

- 演示评审者：CEO、CFO、COO。
- POC 主演示身份：区域经理。
- 主演示闭环：登录 → 查看经营概况 → 发现异常 → AI 归因 → 形成经营建议 → 生成周报。
- 产品边界：区域经理只是首个演示模板，不是工作台唯一用户。

### 2.3 首版角色模板

首版内置两个模板：

1. **区域经理模板**：默认突出辖区概况、异常门店、门店下钻、经营归因和周报入口。
2. **通用默认模板**：提供标准经营概览、指标分析、AI 对话和报表入口。

模板映射规则：

- `manager` 使用区域经理模板。
- `super_admin` 使用通用默认模板，并显示管理后台入口。
- 其他现有角色使用通用默认模板。
- 未知或解析失败的角色安全回退到通用默认模板。

角色模板只决定组件顺序、默认图表、首页重点、推荐问题和空状态文案。模板不得决定数据表、字段、门店范围、指标执行范围或后台操作权限。

## 3. 目标与非目标

### 3.1 目标

- 保留现有登录、指标、报表、归因、权限、MySQL 和 SQL Server 接口。
- 建立“统一工作台 + 角色模板 + 权限驱动”的产品模型。
- 将前台升级为明亮、专业、适合经营决策的双核工作台。
- 将后台升级为按能力域分组的模块化管理系统。
- 拆分大型 SQL、执行器、指标 UI、权限 UI 和单体测试文件。
- 固化三个 Agent 的独立模型、记忆、Prompt 和调用边界。
- 建立自动化测试、浏览器回归、性能检查和完成定义。
- 更新 `AGENTS.md`、`README.md`、`DESIGN.md` 和架构文档。

### 3.2 非目标

- 不建设生产级高可用、集群、灾备或正式监控平台。
- 不增加微服务、消息队列或新的全局状态库。
- 不建设完整财务利润模型；现有数据不包含完整成本、毛利和现金流。
- 不在本轮实现 SQL Server 与 MySQL 的全部固定指标对等查询，但必须保留 SQL Server 接口和适配边界。
- 不实现可视化拖拽工作台或用户自由布局。
- 不部署正式向量数据库；归因 Agent 继续使用可替换的 RAG 端口和 Noop 默认实现。

## 4. 兼容性约束

### 4.1 URL 与协议

以下现有入口保持可用：

- `/login`
- `/`
- `/admin`
- `/api/chat`
- `/api/data`
- `/api/auth/*`
- `/api/admin/*`

`/api/chat` 的 SSE 事件类型、意图元数据、内容事件和完成标记保持兼容。认证 Cookie、HTTP 状态语义和现有管理 API 输入输出保持兼容。

新增后台子路由：

- `/admin/metrics`
- `/admin/reports`
- `/admin/permissions`
- `/admin/data-sources`
- `/admin/agents`

新增工作台内部接口：

- `/api/workbench/context`

该接口返回当前用户的模板标识、可见门店摘要、可用指标/意图标识和管理入口能力，不返回底层表字段策略、凭据或敏感数据。新增接口不改变现有 API 响应。

`/admin` 保留并进入后台概览。内部文件移动期间可以使用短期 re-export 适配，但不得要求现有调用方同步重写。

### 4.2 数据与权限

- 现有 MySQL 表名、字段名、指标口径和日期范围语义不变。
- 现有 `.luminax` 指标、用户、凭据和会话密钥数据可原地读取。
- 现有用户、角色、表权限、字段权限和门店字段值权限语义不变。
- 前端可根据权限隐藏不可用入口，但服务端必须对每次请求重新强制校验。
- 角色模板不能扩大任何数据权限。

## 5. 产品体验设计

### 5.1 工作台骨架

采用“双核经营工作台”：

- 左侧或主区域承载经营概览、指标图表、归因视图和报表。
- 右侧承载持续可用的灵犀助手。
- 用户问题可以驱动主区域切换到对应的图表、报表或归因结果。
- 模板提供默认视图，用户问题和当前分析上下文决定后续视图。

响应式规则：

- 桌面端保持数据视图和 AI 助手并列。
- 平板允许调整两侧宽度或使用受控折叠。
- 移动端使用“经营视图 / 灵犀助手”分段切换，不将双栏强行压缩。
- 360px 至宽屏不得出现文字截断、控件重叠或关键操作不可见。

### 5.2 视觉语言

采用“明亮经营中枢”：

- 白色和浅灰作为主要工作面。
- 深色文字建立信息层级。
- LuminaX 黄色用于品牌线、选中状态和主要动作，不作为大面积背景。
- 红、绿、蓝只用于风险、健康和信息等业务状态。
- 页面区块保持平整、紧凑、可扫描，避免营销式大标题和装饰性卡片堆叠。
- 图标使用现有 Lucide 图标库；熟悉的动作优先图标按钮并提供工具提示。

### 5.3 管理后台

后台采用按能力域分组的侧栏：

- 概览
- 指标管理
- 报表管理
- 权限管理
- 数据源
- Agent 配置

每个能力域独立拥有页面编排、业务组件、客户端请求与状态、应用用例和测试。未实现模块使用清晰的保留状态，不展示伪造的可操作控件。

## 6. 目标架构

### 6.1 分层

1. **产品界面层**：统一工作台、管理后台、登录与会话入口。
2. **HTTP/SSE 兼容层**：鉴权、输入校验、协议转换和错误映射。
3. **应用用例层**：Chat、指标、报表、权限和认证用例。
4. **Agent 编排与领域层**：治理、业务、归因 Agent；经营指标、报表、归因、认证和权限领域能力。
5. **基础设施层**：MySQL、SQL Server、DeepSeek、运行时文件仓库和 RAG 适配器。

### 6.2 路由边界

Next.js 路由只负责：

- 认证与管理员资格检查。
- 请求结构校验。
- 调用一个应用用例。
- 将应用错误映射为 HTTP 或 SSE 响应。

路由不得直接执行 SQL、读取运行时 JSON、拼接 Agent Prompt 或复制权限逻辑。

### 6.3 Agent 边界

**治理 Agent**

- 拥有独立 DeepSeek 模型配置、内存和 System Prompt。
- 先执行本地 Prompt Injection 与敏感数据规则，再调用模型审查。
- 拒绝 Prompt Injection、敏感信息请求和非经营问题。
- 正常输入原样交给业务 Agent。
- 治理模型不可用时失败关闭，不进入业务 Agent。

**业务 Agent**

- 拥有独立 DeepSeek 模型配置、内存和 System Prompt。
- 识别意图、门店、日期范围和自定义指标。
- 调用权限控制、固定 SQL 指标、自定义指标和报表能力。
- 不直接拼接或生成固定指标 SQL。
- 业务解释模型不可用时使用本地格式化结果，不能丢失数据库计算结果。

**归因 Agent**

- 拥有独立 DeepSeek 模型配置、内存和 System Prompt。
- 只接收已经完成权限裁剪的结构化分析数据。
- 负责经营归因和一致的行动建议。
- 可以调用 RAG 端口，但不能自行访问数据库或扩大分析范围。
- RAG 不可用时继续执行无 RAG 归因。

### 6.4 指标与 SQL 边界

- 基础与进阶指标的数值由固定 SQL 或已验证自定义 SQL 在数据库执行。
- Agent 只选择指标、确定门店和日期范围，不自行计算最终数值。
- 固定 SQL 定义与 MySQL 执行器分离。
- 自定义指标 SQL 必须经过只读语法检查、表字段白名单、参数占位符检查、范围注入和测试执行后才能发布。
- SQL 编写 Agent 只生成候选 SQL，不能绕过管理员发布流程。

## 7. 端到端数据流

### 7.1 工作台初始化

1. 认证模块解析当前会话和用户。
2. `/api/workbench/context` 调用模板解析器，根据角色选择区域经理模板或通用默认模板。
3. 服务端根据指标依赖和 AccessControl 生成权限能力摘要，移除用户无权访问的指标、门店范围和管理入口。
4. 前端使用模板标识和能力摘要渲染当前用户工作台。
5. 能力摘要不包含底层表字段权限；后续数据请求仍在服务端重新授权，前端投影不作为安全依据。

工作台上下文的稳定应用模型为：

```ts
interface WorkbenchContext {
  templateId: "regional_manager" | "default";
  availableStoreIds: string[];
  availableMetricCodes: string[];
  availableIntents: string[];
  canAccessAdmin: boolean;
}
```

### 7.2 经营问答

1. 工作台提交问题、会话标识和可选筛选范围。
2. HTTP 适配器解析认证用户。
3. 治理 Agent 审查输入；拒绝时直接返回治理消息。
4. 业务 Agent 识别意图、门店和日期。
5. 权限层根据指标依赖推导所需表、字段和门店范围。
6. 固定 SQL 或已发布自定义 SQL 在授权范围内执行。
7. 业务 Agent 或本地格式化器生成解释内容。
8. API 按兼容 SSE 协议发送意图元数据和内容。

### 7.3 归因

1. 业务 Agent 使用正常固定 SQL 取得分析数据。
2. 权限层在 SQL 执行前完成范围授权。
3. 业务 Agent 将结构化结果和用户问题交给归因 Agent。
4. 归因 Agent 可查询 RAG 端口补充经营知识。
5. 归因 Agent 输出原因、证据、限制和行动建议。

### 7.4 自定义指标

1. 管理员描述指标并选择数据表。
2. SQL 编写 Agent 生成候选 SQL 模板。
3. 系统执行只读、语法、白名单和占位符验证。
4. 系统用受控门店和日期执行测试。
5. 管理员保存草稿或发布。
6. 发布指标进入业务 Agent 的可匹配指标目录。
7. 普通用户调用时仍根据 SQL 真实引用的表和字段执行权限检查。

## 8. 错误处理与可观测性

### 8.1 用户错误

- `400`：输入缺失或格式错误，显示可修正说明。
- `401`：登录失效，跳转登录页并保留安全返回路径。
- `403`：显示缺少数据表、字段或门店范围权限的用户说明。
- 治理拒绝：显示对应治理消息，不伪装成 AI 服务故障。

### 8.2 依赖错误

- 治理模型不可用：失败关闭并提示稍后重试。
- 业务解释模型不可用：返回本地确定性分析结果。
- 数据库不可用或查询超时：返回统一数据源错误，不泄露连接信息或 SQL 参数。
- RAG 不可用：记录降级并继续无 RAG 归因。
- 角色模板解析失败：回退通用默认模板。

### 8.3 POC 可观测性

- 每个请求生成 `requestId`。
- 记录处理阶段、耗时、错误码和所用数据源类型。
- 不记录密码、API Key、Cookie、数据库凭据、个人敏感值或完整 SQL 参数。
- 用户提示与后台诊断分离；前端不展示堆栈和内部错误。

## 9. 组件与文件边界

### 9.1 前台功能域

工作台功能域包含：

- `WorkbenchShell`
- `WorkbenchHeader`
- `ScopeBar`
- `InsightCanvas`
- `AssistantPanel`
- `WorkbenchTemplate`
- `TemplateResolver`
- `RegionalManagerTemplate`
- `DefaultTemplate`
- Overview、MetricAnalysis、Attribution、Report 和 PermissionAwareEmptyState 视图

页面文件只装配工作台功能域。客户端 Hook 负责请求与界面状态，不复制服务端授权逻辑。

### 9.2 后台功能域

指标后台拆为：指标目录、定义编辑器、AI SQL 工作区、验证结果和发布操作。

权限后台拆为：用户目录、用户编辑器、数据访问矩阵、门店范围选择器和权限模拟器。

报表、数据源和 Agent 后台拥有独立路由和保留模块，后续实现时不修改指标或权限页面的内部状态。

### 9.3 后端重点拆分

- `mysql-metric-queries.ts` 按 achievement、trend、mix、promotion、refund、anomaly、compare、attribution 和 report 指标族拆分。
- MySQL 执行器拆为请求调度、参数绑定、行映射和结果装配，继续实现 `SqlMetricQueryExecutor`。
- Business Agent 保持稳定公共接口，内部拆出请求解析、固定/自定义指标执行和结果解释职责。
- 测试按 agents、auth、chat、metrics、permissions、reports 和 workbench 归属拆分。
- 共享 FakeModel、测试用户、指标和数据集放入 `tests/fixtures`。

## 10. 测试与验收

### 10.1 自动化测试

**单元与领域测试**

- 角色模板解析、角色映射和安全回退。
- 三 Agent 的模型、记忆、Prompt 和调用契约。
- 权限表、字段和门店值授权。
- 固定 SQL 参数绑定、结果映射和指标依赖。
- 自定义指标 SQL 验证和发布。
- 报表模型、归因模型和本地解释降级。

**接口与集成测试**

- API 状态码和响应结构。
- SSE 事件顺序、元数据和内容。
- 登录、Cookie、密码重置和会话失效。
- MySQL 只读账号真实查询。
- 自定义指标完整发布与调用链路。

**浏览器回归**

- 登录与退出。
- 区域经理模板和通用模板。
- 桌面双栏与移动分段视图。
- 正常指标、权限拒绝、自定义指标、归因和周报。
- 指标管理和权限管理主要流程。
- 桌面与移动截图无重叠、空白画布或不可见操作。

### 10.2 非功能门槛

- 在本地 MySQL、连接池已建立、现有 5 店 14 天 POC 数据规模下，单次固定 SQL 执行目标不超过 1.5 秒；该目标不包含 DeepSeek 解释耗时。
- 非 AI 的纯客户端页面交互，从输入事件到可见状态更新目标不超过 200ms。
- AI 请求有明确加载状态和超时提示。
- 数据库连接、查询和 Agent 模型调用均设置超时。
- 360px 至宽屏无文字和控件重叠。
- 键盘可以完成登录和主要操作。
- 密钥、运行数据和视觉伴侣数据不进入 Git。

### 10.3 每阶段完成定义

- 新增或修改行为先有失败测试。
- 相关单元、接口和浏览器回归通过。
- TypeScript、ESLint 和生产构建通过。
- 文档与代码同步。
- 浏览器验证真实用户路径。
- Git 提交不包含密钥、运行数据或无关文件。
- 每个阶段形成独立提交并推送到 `origin/main`；实施计划另行决定是否使用工作分支或 worktree。

## 12. 文档职责

### 12.1 AGENTS.md

`AGENTS.md` 是 AI Agent 和开发者的项目级事实来源，必须包含：

## 13. 风险与控制

| 风险 | 控制措施 |
|---|---|
| 完整重构造成行为回归 | 先建立 API 和核心流程兼容测试，按垂直切片替换 |
| 角色模板与权限混淆 | 模板只输出 UI 默认值，所有权限由服务端 AccessControl 强制 |
| SQL 拆分改变口径 | 在拆分前后对同一门店和日期执行结果对比测试 |
| UI 重构阻断演示 | 每阶段保持可运行，工作台和后台分别迁移 |
| DeepSeek 输出不稳定 | 治理使用本地规则和确定性校正，业务解释保留本地降级 |
| 文档再次漂移 | `AGENTS.md` 纳入每阶段完成定义并随代码提交 |
| Git 泄露凭据 | 持续忽略 `.env.local`、`.luminax/`、`.superpowers/` 和日志，提交前扫描 |

## 14. 成功标准

重构完成时必须同时满足：

1. 现有 API、登录、权限、指标、归因和报表流程兼容。
2. 工作台采用统一能力底座，区域经理模板与通用模板可以稳定解析和回退。
3. 模板不能绕过服务端表、字段和门店值权限。
4. 前台采用已批准的明亮双核经营工作台，并完成移动端适配。
5. 后台按能力域组织，指标与权限页面不再由单一超大组件承担。
6. 固定 SQL 定义和 MySQL 执行器按职责拆分，计算结果与重构前一致。
7. 三 Agent 继续拥有独立模型、记忆和 Prompt，归因 RAG 接口可替换。
8. 测试按模块组织，类型检查、Lint、测试、生产构建和浏览器回归通过。
9. `AGENTS.md`、`README.md` 和 `DESIGN.md` 与实际系统一致。
10. GitHub `origin/main` 中不包含密钥、运行数据或本地会话文件。
