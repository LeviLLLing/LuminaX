# LuminaX 混合业务意图路由设计

## 与洞察框架的边界

本设计独立于《LuminaX 全意图洞察优先级框架设计》。两者解决不同问题：

- 混合业务意图路由负责理解“用户想分析什么”，把自然语言映射为受控 `AnalysisIntent`。
- 全意图洞察优先级框架负责理解“SQL 结果中什么值得关注”，对已经确定的意图执行固定业务策略。

意图路由不读取或评价 SQL 数值，洞察策略不解析用户自然语言。两者只通过 `AnalysisIntent` 枚举连接。

## 背景与问题

当前 Business Agent 使用 `classifyIntent` 对问题进行关键词和正则匹配。日期与门店实体提取适合确定性解析，但经营意图只靠关键词存在明显局限：

- “分析所有门店的销售情况”没有“比较”关键词，会落入默认的 `achievement_rate`。
- 同义表达、复合问题和省略表达容易错分。
- 默认意图掩盖了分类不确定性，后续 SQL、Chatbox 和洞察都会在错误意图上保持内部一致。

治理 Agent 已经使用 DeepSeek 判断安全与业务相关性，但其职责是允许或拒绝请求，不应同时承担指标路由。业务意图应由 Business Agent 内部的专用路由组件处理。

## 目标

- 使用 DeepSeek 理解正常经营问题的语义意图，而不是只依赖关键词。
- 日期、门店和 UI 选择范围继续由确定性解析与权限系统控制，模型不能修改。
- 模型只能从允许的系统意图枚举中选择，不能生成 SQL、指标名或任意工具调用。
- 模型超时、无效、低置信度或不可用时，自动回退到改进后的确定性分类器。
- 已发布自定义指标继续由注册表名称、代码和别名精确匹配，不交给模型猜测。
- 保持 Business Agent、治理 Agent、归因 Agent 三 Agent 架构，不新增第四个运行时 Agent。
- 控制额外延迟与 Token：路由提示词短、输出小、无 SQL 数据、无完整聊天回答。

## 非目标

- 不让路由模型决定请求是否敏感、是否属于 LuminaX 范围；这是治理 Agent 的职责。
- 不让路由模型提取最终日期、门店 ID 或权限范围。
- 不让路由模型计算指标、选择洞察关注对象或生成经营建议。
- 不允许路由失败阻断合法经营请求。
- 不改变公开 SSE `intent` 事件结构或现有 `AnalysisIntent` 字符串值。

## 方案

采用“模型语义路由 + 确定性实体解析 + 严格校验 + 规则回退”。

完全使用规则速度快，但无法稳定覆盖自然表达。完全依赖模型语义更强，但存在超时、格式漂移和不可重复问题。混合方案让模型解决语言理解，让确定性代码控制查询边界和故障恢复。

## 组件设计

### BusinessIntentRouter

在 `src/modules/intent/` 增加业务意图路由端口：

```ts
interface BusinessIntentRouter {
  route(input: BusinessIntentRouteInput): Promise<BusinessIntentRouteResult>;
}
```

输入只包含：

- 当前用户问题；
- 当前 UI 范围提示：`single_store | multi_store | all_stores | unspecified`；
- 可选的上一条用户问题，用于理解“那退款呢”等轻量追问；
- 允许的系统意图及其简短定义。

上一条问题最多保留三百个字符，不提供历史回答、SQL 结果、权限明细或数据库信息。当前问题始终优先于历史上下文。

返回内部结果：

```ts
interface BusinessIntentRouteResult {
  intent: SystemAnalysisIntent;
  confidence: number;
  source: "model" | "fallback";
  fallbackReason: string | null;
}
```

`SystemAnalysisIntent` 排除 `irrelevant` 和 `custom_metric`。前者由治理流程处理，后者由自定义指标注册表确定。

### ModelBusinessIntentRouter

模型路由器使用单独的 `DeepSeekChatModel` 实例，但它只是 Business Agent 的内部组件，不是拥有独立职责和记忆的新 Agent。

配置优先级：

```text
DEEPSEEK_INTENT_MODEL
DEEPSEEK_BUSINESS_MODEL
DEEPSEEK_MODEL
deepseek-v4-flash
```

使用 `DEEPSEEK_INTENT_TIMEOUT_MS`，默认八秒；温度为零。模型只返回：

```json
{"intent":"compare","confidence":0.92}
```

提示词包含每个系统意图的边界和少量易混淆示例，明确以下语义：

- 多门店或全部门店的宽泛“销售情况、经营表现”优先为 `compare`。
- 单店或整体的目标完成、销售是否达标为 `achievement_rate`。
- “为什么、原因、驱动”且要求解释表现为 `attribution`。
- 只有明确要求周报或报告时才为 `report`。
- 渠道结构、时段结构、促销、退款、异常、订单趋势和客单价趋势分别路由到对应意图。

模型不得返回解释、实体、日期、门店、SQL、工具参数或建议。

### 输出校验

模型结果必须同时满足：

- 能解析为单一 JSON 对象；
- `intent` 属于系统意图白名单；
- `confidence` 是零到一之间的有限数值；
- 不包含路由合同之外的执行指令；
- 置信度大于等于 `0.70`。

任一条件不满足即进入确定性回退。模型返回 `irrelevant`、`custom_metric` 或未知意图也视为无效，不扩大权限或执行范围。

### 确定性实体解析

现有确定性代码继续负责：

- 提取 ISO 日期和中文月日范围；
- 识别合法门店编号和已登记门店名称；
- 合并 UI 已选择的门店与日期范围；
- 使用默认日期范围；
- 调用 `AccessControl.authorizeScope` 执行表、字段和门店值权限校验。

模型路由结果只替换 `intent`，不得覆盖任何实体解析结果。即使模型提示中出现门店或日期，执行层也只接受确定性解析器与 UI 上下文产生的范围。

### 自定义指标优先级

治理通过后，系统先使用 `CustomMetricRuntime.match` 对已发布指标的名称、代码和别名执行确定性匹配：

1. 唯一匹配已发布自定义指标时，直接使用 `custom_metric`，跳过系统意图模型路由。
2. 没有匹配时，进入模型系统意图路由。
3. 多个自定义指标冲突时沿用最长匹配优先；同分冲突不能静默猜测，应回退为无匹配并记录冲突原因。

模型不能主动选择未被注册表匹配的自定义指标。

### 确定性回退分类器

保留 `classifyIntent`，但把它收敛为故障回退而不是主要语义理解器，并补充宽泛销售问题规则：

- 明确周报、归因、订单趋势、客单价、渠道、时段、促销、退款、异常和对比关键词沿用现有映射。
- 问题包含“所有门店、全部门店、各门店、多门店”以及“销售情况、经营情况、门店表现”等宽泛表达时，回退为 `compare`。
- UI 范围明确包含多家门店且问题是宽泛销售或经营分析时，回退为 `compare`。
- 单家门店或无多店信号的达标、销售目标问题回退为 `achievement_rate`。
- 无法可靠识别时使用 `achievement_rate` 作为兼容默认值，同时在内部标记 `fallbackReason`，不对用户暴露技术细节。

日期和门店正则仍属于实体解析，不属于业务语义策略。

## 请求流程

1. Governance Agent 执行本地安全规则和 DeepSeek 治理审核。
2. 拒绝请求直接返回，不调用 Business Intent Router，也不更新洞察。
3. 允许请求进入 Business Agent，确定性提取日期、门店和 UI 范围提示。
4. 已发布自定义指标执行确定性匹配；匹配成功则直接进入自定义 SQL 流程。
5. 系统指标请求调用 Model Business Intent Router。
6. 校验有效且置信度达标时采用模型意图，否则调用确定性回退分类器。
7. Business Agent 根据最终意图申请权限并执行对应固定 SQL。
8. Chatbox 使用完整 SQL 结果生成回答。
9. 全意图洞察优先级框架根据同一个最终意图和 SQL 结果生成洞察与行动。

## 记忆与追问

- Intent Router 本身保持无状态，不拥有独立 Agent Memory。
- Business Agent 从自己的会话记忆中只提取最近一条用户问题作为可选语义上下文。
- 不把上一条完整回答、洞察、SQL 数据或治理决策传给路由模型。
- 当前问题包含明确意图时必须覆盖上一轮意图；只有当前表达省略语义时才参考上一条问题。
- 路由结果仍由 Business Agent 记忆边界管理，不创建第四套 Agent 记忆。

## 错误处理与降级

- 模型超时、网络错误、空响应、非法 JSON、未知意图或低置信度：静默使用规则回退。
- 规则回退同样失败：使用兼容默认意图，并让 Business Agent 在回答中说明分析口径，而不是报系统错误。
- 自定义指标冲突：不执行任一自定义 SQL，继续系统意图路由并记录冲突。
- 无效门店或无授权门店：沿用现有权限和业务错误，不接受模型建议的替代门店。
- 路由成功后 SQL 失败：沿用 Business Agent 现有数据错误处理，不重新调用模型选择另一个意图。

## 可观测性

仅记录不含原始问题和敏感信息的路由指标：

- 最终意图；
- 路由来源 `model | fallback | custom_metric`；
- 置信度区间；
- 路由耗时；
- 回退原因代码；
- 模型与规则是否存在分歧。

不得记录完整用户输入、会话 Cookie、权限值、模型原始响应或数据库参数。

## 测试与验收

采用聚焦测试覆盖以下行为：

- “分析五月一日至五月七日所有门店的销售情况”路由为 `compare`。
- 单店“销售目标完成得怎么样”路由为 `achievement_rate`。
- 明确退款、订单趋势、客单价、渠道、时段、促销、异常、归因和周报问题路由正确。
- 已发布自定义指标名称或别名匹配时跳过系统模型路由。
- 模型空响应、超时、非法 JSON、未知意图和低置信度均使用规则回退。
- 模型返回的门店或日期字段即使存在也不能改变确定性范围。
- 治理拒绝请求不调用路由器、不执行 SQL、不更新洞察。
- 轻量追问可参考上一条用户问题，明确的新意图覆盖历史意图。
- 最终 SSE `intent` 事件和 Business Agent 公共返回合同保持不变。

硬性验收：用户提出“分析 2025-05-01 至 2025-05-07 所有门店的销售情况”时，模型正常和模型不可用两条路径都必须得到 `compare`；门店范围和日期范围必须分别保持全部授权门店与指定日期，不得由模型改写。

## 与洞察设计的集成合同

- 本设计输出唯一最终 `AnalysisIntent`。
- 洞察优先级框架只接收最终意图、授权 SQL 结果和权限范围。
- 洞察框架不得再次识别或纠正用户意图。
- 若后续新增系统意图，必须同时注册路由定义、固定 SQL、权限需求和洞察关注策略；缺少任一项时不能启用。
