# LuminaX 全意图洞察优先级框架设计

## 背景与问题

LuminaX 的 Chatbox 使用固定 SQL 的完整结构化结果生成经营分析，但“洞察与行动”会先把结果转换为事实候选，再由 DeepSeek 选择发现。部分意图使用通用递归采集器，并在少量数值后停止；确定性回退又直接选择候选数组前几项。这使 SQL 行顺序、对象字段顺序和模型稳定性错误地影响了经营关注对象。

2025-05-01 至 2025-05-07 的全部门店目标达成分析就是一个明确案例：SQL 与 Chatbox 指出地铁站店和社区中心店表现较弱，但洞察候选只覆盖排在首位的上海商场店，最终错误要求关注上海商场店。

这不是某一个指标的孤立问题。只修复目标达成仍会让订单、客单价、退款、结构分析、周报和自定义指标继续受到同类问题影响，因此需要建立覆盖全部经营分析意图的统一优先级框架。

## 目标

- 洞察完整评估当前用户、门店和时间权限范围内的所有 SQL 事实。
- “关注什么”由可测试的确定性业务策略决定，不由 SQL 行顺序或 DeepSeek 决定。
- 每个分析意图具有与其业务语义相符的关注规则，不能对没有目标或基准的指标武断判断好坏。
- 优先覆盖不同门店、日期或经营维度，避免同一主体的多个基础数值占满所有发现。
- DeepSeek 负责待验证假设和行动措辞，但不能替换或改写已确定的核心事实。
- 模型失败、超时或输出不合规时，确定性回退仍产生一致、完整且可执行的洞察。
- 没有明显异常时仍成功更新洞察，并明确“暂无重点风险”，不制造虚假风险。
- 保持现有 SQL、权限边界、SSE 协议、洞察 API 和本地运行时仓库兼容。

## 非目标

- 不把指标计算迁回 Agent；数值仍只来自固定 SQL 或已发布自定义 SQL。
- 不在本阶段新增跨期同比、环比或额外数据库查询。
- 不把相关性写成已证实因果；缺少驱动证据时只能提出待验证假设。
- 不改变治理 Agent 的拒绝策略。敏感、注入或无关问题继续直接拒绝且不更新洞察。

## 方案选择

采用“完整事实目录 + 意图策略注册表 + 确定性关注计划 + 模型受约束表达”。

未采用“把全部原始结果直接交给 DeepSeek”的方案，因为它消耗更多 Token，结论会随模型状态变化，也无法保证 Chatbox 与洞察一致。未采用单一全局评分公式，因为达成率、退款率、结构占比和归因贡献的业务含义不同，强行归一会产生伪精确结论。

## 核心架构

### 完整事实目录

`InsightSourceCatalog` 继续负责把授权后的 SQL 结果转换为可引用事实与证据，但必须满足：

- 系统意图使用专用构建器，遍历全部门店、日期和维度，不做“前几个数值”式截断。
- 每个事实保留指标代码、主体、数值、单位、证据和用于排序的语义元数据。
- 语义元数据包括事实角色、比较基准、差额、指标方向和主体分组，仅在服务端使用，不进入公开 API。
- `report` 和 `achievement_rate` 不再使用通用事实采集器。
- `custom_metric` 可以保留通用结构解析，但不得在缺少指标洞察策略时自行判定正负。

### 意图策略注册表

新增 `InsightAttentionStrategy` 接口，并按 `AnalysisIntent` 注册策略。每个策略接收完整事实目录，输出 `InsightAttentionPlan`：

- 已排序且必须保留的核心发现；
- 每条发现的严重程度、证据和主体；
- 可选的支持性发现；
- 待核查上下文和允许使用的验证指标；
- 无风险或无数据时的状态。

策略注册表是唯一负责“什么值得关注”的模块。事实目录不做业务判断，DeepSeek 不做关注对象选择，Validator 不重新排序。

### 主体去重与候选配额

统一选择流程如下：

1. 先按意图策略计算风险或关注顺序。
2. 第一轮每个主体最多选择一条主要发现，最多五条。
3. 第二轮才补充同一主体的目标差额、驱动或范围级事实。
4. 未达标、异常或风险主体必须排在正常主体之前。
5. 正常主体不能仅为凑足数量而被描述成风险。
6. 没有风险时允许一至三条正向或中性发现，不再强制制造三条风险。

### 确定性发现与模型职责

关注计划锁定 `sourceId`、`severity` 和 `evidenceIds`。Insight Composer 不再让 DeepSeek 自由选择 findings，而是把确定性发现与行动上下文提供给模型。

DeepSeek 只负责：

- 撰写明确标记为待验证的原因假设；
- 为指定关注主体生成行动建议、负责人和优先级；
- 使用计划允许的验证指标。

洞察标题、发现标题、事实摘要和数值继续由服务端从 SQL 来源派生；Chatbox 的完整经营描述继续由 Business Agent 独立生成。模型输出缺失必要行动上下文、引用未知上下文、包含非法数值或因果断言时，系统使用同一关注计划生成确定性草稿。公开的 `InsightSnapshot`、SSE 事件和 Chatbox 内容格式保持不变。

## 各意图关注策略

### 销售达成 `achievement_rate`

- 达成率低于 100% 即未达标，按达成率从低到高排序。
- 低于 90% 为高关注，90% 至低于 100% 为中关注，达到或超过 100% 为正向。
- 每个未达标门店先选择达成率，再以负向目标差额作为支持事实。
- 全部门店达标时展示整体达成和最低达成率门店的正向跟踪，不生成整改结论。

### 门店对比 `compare`

- 首要依据仍是目标达成率和目标差额，不能把销售额较小直接解释为经营较差。
- 先覆盖未达标门店，再按退款率、订单量和客单价的跨店偏离补充待核查信号。
- 缺少统一目标或基准的订单量、客单价只描述差异，不直接断言异常。
- 同达成率时按负向目标差额比例、退款率和稳定门店 ID 依次排序。

### 订单趋势 `order_trend`

- 订单目标达成率低于 100% 或趋势变化率为负时进入关注范围。
- 达成率低于 90% 或趋势下降达到 10% 为高关注；其余未达标或下降为中关注。
- 先按达成率缺口，再按趋势下降幅度排序；正常增长门店只作为正向信号。

### 客单价趋势 `aov_trend`

- 客单价差额为负或趋势变化率为负时进入关注范围。
- 实际客单价低于目标 10% 以上或趋势下降达到 10% 为高关注；其余负向差异为中关注。
- 平均客单价、目标客单价只作为差额证据，不能各自占用不同门店的主要发现名额。

### 退款分析 `refund_rate`

- 退款率和取消率越高风险越高，门店与日期按比率降序排列。
- 延用周报已存在的 2% 退款率警戒线：高于 2% 为高关注。
- 未超过警戒线、但高于当前范围整体退款率至少 0.5 个百分点的门店为中关注；其余为低关注或正向。
- 行动只要求核查退款原因、出品和履约记录，不在没有明细证据时断言具体原因。

### 异常检测 `anomaly_detection`

- 先按异常日数量降序，再按异常日标准分绝对值和销售目标缺口排序。
- 两个及以上异常日为高关注，一个异常日为中关注，无异常日为正向。
- 主要发现按门店去重；具体异常日期作为支持证据和核查项。

### 渠道结构 `channel_mix` 与时段结构 `daypart_analysis`

- 占比高低本身不代表好坏，因此默认输出结构性、中性发现。
- 优先展示占比最高的结构、集中度明显的结构，以及同一维度在门店之间差异最大的项目。
- 没有历史基准、目标或收益率时，不使用“异常、下滑、低效”等结论。
- 行动以核查容量、毛利、客群或运营配置为主，并明确需要补充业务基准。

### 促销贡献 `promotion_contribution`

- 促销贡献率和优惠额没有 ROI、毛利或目标基准时只作为中性结构事实。
- 优先展示贡献集中度和门店间差异，不把高优惠额自动判定为风险或成效。
- 行动要求核查促销增量、毛利和复购证据；只有后续存在明确基准时才产生正负严重程度。

### 经营归因 `attribution`

- 当总差额为负时，按负向贡献绝对值从大到小选择驱动，并优先覆盖不同维度。
- 最大负向驱动为高关注，其余负向驱动为中关注；正向驱动作为对冲因素，不覆盖主要风险。
- 当总差额非负且无负向驱动时，输出正向贡献和持续跟踪行动。
- Attribution Agent 的自然语言结论不能替代 SQL 分解结果，只能解释和提出验证建议。

### 经营周报 `report`

- 使用周报完整事实目录，不再取通用对象中的前几个数值。
- 综合目标达成、尾部门店、退款率和异常日期生成关注计划。
- 范围整体达成率低于 95%、门店达成率低于 90%、退款率高于 2% 延用现有周报警戒规则；其他低于 100% 的门店仍作为中关注。
- 同一风险不得在趋势总结、需关注信息和洞察中被重复包装成多个独立问题。

### 自定义指标 `custom_metric`

- 指标注册表增加可选且向后兼容的 `insightPolicy`，结构包含：
  - `direction`: `higher_is_better | lower_is_better | target_is_best | neutral`
  - `benchmark`: `absolute | target | scoped_average | none`
  - `warningThreshold`: 可选有限数值
  - `criticalThreshold`: 可选有限数值
  - `targetValue`: 使用 `target_is_best` 或 `target` 基准时必填的有限数值
- `absolute` 基准直接按指标方向比较实际值与阈值；`target` 和 `scoped_average` 基准把阈值解释为相对基准的非负偏离百分比。
- `higher_is_better` 在低于阈值时产生风险，`lower_is_better` 在高于阈值时产生风险，`target_is_best` 按偏离目标的绝对幅度产生风险，`neutral` 永不自动产生风险。
- 注册和发布校验必须保证严重阈值比警戒阈值更深入风险区间；无效组合不能发布。
- 已有注册表记录没有该字段时仍可正常读取和执行，但洞察只能生成中性事实与“需要配置判断口径”的行动。
- 配置策略后才允许按阈值产生高、中、正向分类。
- 第二实施批次在管理后台通过同一可选字段配置策略；Agent 不根据指标名称猜测好坏方向。

### 无数据与拒绝请求

- 合法经营问题没有数据时成功更新为“当前范围暂无可用经营数据”。
- 治理 Agent 拒绝的敏感、注入或无关问题不触发洞察更新，直接返回拒绝结果。

## 行动生成规则

- 行动只能围绕关注计划中的主体和事实生成。
- 每个高关注主体至少有一项行动；默认最多生成三项，避免行动列表失焦。
- 高关注默认 `P0`，中关注默认 `P1`，低关注或正向跟踪默认 `P2`。
- 已有直接驱动证据时可提出针对性改善动作；只有结果信号时只能提出核查动作。
- 每项行动必须绑定允许的验证指标，且不得包含 SQL 未提供的数值承诺。
- 全部正常时生成持续跟踪或复制优秀做法的行动，不生成整改动作。

## 数据流

1. Business Agent 选择意图和授权范围，并执行现有固定 SQL 或已发布自定义 SQL。
2. 专用事实目录完整转换结构化结果，不丢弃后排门店或维度。
3. 意图策略生成确定性关注计划并执行主体去重。
4. Insight Composer 基于锁定发现请求 DeepSeek 完善假设与行动。
5. 模型失败时，确定性回退使用同一计划生成完整快照。
6. Validator 校验证据、权限和文本边界，Repository 保存最新洞察。
7. Chatbox 继续返回完整经营分析；洞察与 Chatbox 使用同一份 SQL 数据和同一经营口径。

## 错误处理与兼容

- 单个无效数值只跳过对应事实，不影响其他门店生成洞察。
- 策略无法判断正负时降级为中性，不猜测业务语义。
- 模型输出违反关注计划时回退，不向用户显示“洞察更新失败”。
- 只有权限、SQL、持久化等无法形成权威事实的错误才进入现有失败生命周期。
- `insightPolicy` 为可选字段，旧注册表 JSON 无需迁移即可读取。
- 不变更公开 API、SSE 事件字段、MySQL 查询接口或 SQL Server 适配器接口。

## 测试与验收

采用表驱动的聚焦测试，控制测试成本：

- 每个系统意图至少覆盖一个风险场景和一个无风险场景。
- SQL 第一家门店正常、后续门店异常时，排序必须与行顺序无关。
- 多家异常门店必须先各占一条主要发现，再补充同主体支持事实。
- 结构类和无策略自定义指标不得生成无基准的风险结论。
- DeepSeek 空响应、非法 JSON、缺失主体和越权引用均回退到相同关注计划。
- 无数据合法请求更新成功，治理拒绝请求不更新。
- 现有权限、并发、持久化、SSE 和 Chatbox 完整回答测试继续通过。

本案例硬性验收：分析 2025-05-01 至 2025-05-07 全部门店销售情况时，洞察必须优先覆盖实际未达标的地铁站店和社区中心店；上海商场店只有在自身满足对应关注规则时才能作为风险出现。

## 实施边界

实施按两个连续批次完成，但属于同一设计范围：

1. 建立完整事实目录、策略注册表、确定性关注计划和全部系统意图策略。
2. 增加向后兼容的自定义指标 `insightPolicy`，并让无策略指标保持中性。

两个批次均不改变公开接口；第一批完成后即可消除当前错误关注门店的问题，第二批补齐管理员可配置指标的判断语义。
