# LuminaX 目标达成洞察优先级设计

## 背景与问题

当用户分析多门店销售目标达成情况时，业务回答会展示全部门店，但洞察投影当前通过通用递归采集器提取事实，并在五个数值后停止。数据从第一家门店开始遍历，因此洞察候选可能只包含第一家门店。DeepSeek 无有效输出时，确定性回退又直接选择候选数组前三项，导致“SQL 返回顺序”被误当成“经营关注优先级”。

本次案例中，上海商场店位于结果首位，地铁站店和社区中心店未达标；洞察却选择上海商场店的销售额、目标和差额。这不是 SQL 计算错误，而是事实目录截断和回退排序错误。

## 目标

- 目标达成洞察必须完整评估当前授权范围内的全部门店。
- 关注对象由固定业务规则决定，不依赖 SQL 行顺序或模型稳定性。
- 达成率低于 100% 的门店优先于已达标门店；未达标门店按达成率从低到高排序。
- 达成率低于 90% 标记为高关注，90% 至低于 100% 标记为中关注，达到或超过 100% 标记为正向。
- 洞察优先覆盖不同的未达标门店，避免同一家门店的销售额、目标和差额占满全部发现。
- 行动绑定已选择的未达标门店和验证指标；缺少驱动证据时只提出核查要求，不生成未经 SQL 支持的因果结论。
- DeepSeek 失败、超时或返回不合规内容时，确定性回退仍生成相同关注对象。

## 非目标

- 不修改目标达成 SQL、数据库结构、权限模型或门店数据。
- 不新增订单、客单价、退款等额外 SQL 调用。
- 不修改 Chatbox 的完整经营分析、SSE 事件或公开洞察 API 结构。
- 不改变其他意图已有的洞察规则；通用指标和报表仍保留现有通用目录。

## 方案选择

采用“专用事实目录 + 确定性关注计划 + 模型受约束表达”。

未采用仅扩大 DeepSeek 输入的方案，因为它增加 Token 消耗，且无法保证模型每次选择相同门店。未采用额外执行门店对比 SQL 的方案，因为本次只需要修复目标达成洞察的一致性；订单、客单价和退款驱动可在后续归因增强中加入。

## 组件设计

### 目标达成事实目录

`insight-source-catalog` 为 `achievement_rate` 使用专用构建函数，不再调用最多采集五个数值的通用构建函数。

目录读取全部门店，并为每家门店建立以下 SQL 权威事实：

- 目标达成率，作为门店关注排序和严重程度的主要指标。
- 销售目标差额，作为未达标事实的支持指标。
- 销售额和销售目标，作为证据展示所需的基础事实。

同时建立跨门店达成率证据和销售额对目标证据，使每条发现都能链接到包含全部门店的可核验数据。整体达成率和整体差额可以作为范围级补充事实，但不能覆盖未达标门店的优先位置。

### 确定性关注计划

新增纯函数，根据事实目录生成关注计划：

1. 找出所有达成率低于 100% 的门店。
2. 按达成率升序排序，相同时按稳定门店 ID 排序。
3. 优先选择每个未达标门店的一条达成率事实，最多五家，确保门店去重覆盖。
4. 当未达标门店少于三家时，使用这些门店的负向目标差额和整体达成率补足模型所需候选，但不引入已达标门店作为风险发现。
5. 当不存在未达标门店时，选择整体达成率和达成率最低的门店作为正向跟踪项，标题明确当前范围无未达标门店。

严重程度固定映射：

- 达成率低于 90%：`high`
- 达成率大于等于 90% 且低于 100%：`medium`
- 达成率大于等于 100%：`positive`
- 支持性差额事实继承对应门店的严重程度

### 模型约束与回退

Insight Composer 只把关注计划中的事实候选交给 DeepSeek，不再让模型从未排序的完整数组中任意选择。模型输出必须包含关注计划要求的未达标门店主要事实；缺失、超时、格式错误或语义校验失败时，使用同一关注计划生成确定性草稿。

因此 DeepSeek 只负责：

- 在证据边界内撰写待核查假设；
- 生成不含虚构数值和因果结论的行动措辞；
- 选择允许的负责人、优先级和验证指标。

DeepSeek 不负责决定哪家门店表现最差。

### 行动生成

确定性回退为优先级最高的两家未达标门店分别生成行动：

- 高关注门店使用 `P0`，中关注门店使用 `P1`。
- 行动标题明确对应门店，并要求核查销售差距及订单量、客单价等可能驱动。
- 订单量和客单价只作为待核查项，不表述为已确认原因。
- 验证指标使用该门店的目标达成率；公开 API 结构保持不变。

若全部门店达标，则生成持续跟踪行动，不制造风险或待整改结论。

## 数据流

1. Business Agent 执行现有固定目标达成 SQL，并得到授权范围内的 `overall` 和 `stores`。
2. Insight Application 将同一份结构化结果交给目标达成事实目录。
3. 关注计划对全部门店进行确定性分类、排序和去重选择。
4. Insight Composer 在受限候选内请求 DeepSeek；失败时按关注计划回退。
5. Validator 继续从目录派生标题、发现标题、摘要和观察事实，并校验证据引用。
6. Latest Insight Repository 保存与 Chatbox 使用同一 SQL 数据范围生成的快照。

## 错误处理

- 无门店数据时沿用“当前范围暂无可用经营数据”的成功洞察，而不是制造异常门店。
- 门店缺少有效达成率时不参与风险排序；若全部无效，则返回数据可用性洞察。
- 模型输出未覆盖必须关注的门店、引用未知来源或产生非法内容时，静默使用确定性草稿。
- 权限、并发令牌和持久化失败继续沿用现有 Insight Application 生命周期，不改变安全边界。

## 测试与验收

新增聚焦测试，不扩大整套测试成本：

- SQL 第一家门店已达标，后续地铁站店和社区中心店未达标时，关注计划必须先选择后两家。
- 同一家门店的销售额、目标和差额不能挤掉另一家未达标门店的主要发现。
- 低于 90%、90% 至低于 100%、达到 100% 的严重程度映射正确。
- DeepSeek 返回空值或非法 JSON 时，回退结果仍关注同样的未达标门店。
- 全部门店达标时输出正向跟踪，不出现高关注或中关注风险。
- 现有洞察物化、权限和 SSE 合同测试继续通过。

本案例验收结果：对 2025-05-01 至 2025-05-07 的全部授权门店执行目标达成分析时，洞察必须优先覆盖地铁站店和社区中心店，上海商场店只有在其自身未达标或作为非风险补充事实时才可出现。
